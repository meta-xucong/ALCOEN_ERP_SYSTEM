# AI CATS 研究/实验模块开发文档

## 背景

AI CATS 当前已经完成“配件生产”模块的闭环能力，包含工件库、质量控制、质量检测、验收四个子流程。  
“研究/实验”模块需要作为 AI CATS 的平级模块独立存在，但整体工作方式可以直接借鉴“配件生产”的成熟结构，降低开发成本和用户学习成本。

本模块的核心业务语义不是“生产质控”，而是“研究发起、指导审批、共同验收、阶段归档”。

---

## 目标

1. 在 AI CATS 内新增一套独立的“研究/实验”业务模块。
2. 保持与“配件生产”接近的页面结构、操作节奏和状态闭环。
3. 将原“质控人”角色在本模块中显示为“研发人员”。
4. 将原“质检人”角色在本模块中显示为“指导/验收人员”。
5. 将原“图纸、作业指导书、检测点、备注”等生产语义，替换为研究场景下更自然的术语和材料结构。
6. 支持 A 侧发起研究、上传材料，B 侧审批并给出建议，双方共同验收后完成该阶段研发。

---

## V1 实施修正

结合当前代码基座和后续扩展性，文档补充以下 V1 落地约束：

1. **数据模型独立**  
   研究模块必须使用独立数据表，不直接复用“配件生产”模块的 `qc_workpieces`、`qc_work_orders` 等生产主表。

2. **交互骨架复用**  
   允许复用的内容包括：
   - 页面布局风格
   - 动态附件表单
   - 批次历史记录机制
   - QC 角色权限判断模式
   - 文件上传与图片/非图片预览逻辑

3. **项目模板 -> 批次快照机制**  
   研究批次创建后，不应实时引用项目模板附件，而应复制为批次级快照。  
   这样可以保证：
   - 历史批次不受后续模板修改影响
   - 审批意见与验收结论始终对应当时版本
   - 后续支持多轮退回补充时，数据边界更清晰

4. **V1 闭环优先于高级能力**  
   第一版先保证以下动作全闭环：
   - 新增/编辑/删除研究项目
   - 新增/编辑/删除研究批次
   - 提交指导审批
   - 审批通过 / 退回补充
   - 双方共同验收
   - 取消确认
   - 验收后回退
   - 全流程历史记录留痕

## 设计原则

### 1. 平级独立，不与配件生产共用业务表

“研究/实验”是 AI CATS 的平级模块，不应直接复用 `qc_workpieces`、`qc_work_orders` 等生产业务数据表。  
推荐复用的是页面骨架、交互组件、附件上传逻辑、历史记录机制和权限判断模式，而不是直接把研究数据塞进生产表里。

### 2. 工作方式一致，业务语义切换

用户在“研究/实验”模块中的使用习惯，尽量与“配件生产”一致：

1. 先建立基础项目模板
2. 再发起具体批次
3. 再进入指导审批
4. 最后进入共同验收

但每一步的名称、字段和附件类型，改为研究语义。

### 3. 先做 MVP 闭环，再做深度分析能力

第一阶段先把流程闭环搭好，不急着引入复杂统计分析、图表引擎、实验数据解析、版本对比等高级能力。  
优先保证“可发起、可审批、可退回、可共同验收、可追溯”。

## 模块形态

“研究/实验”模块建议包含 4 个子页面，与“配件生产”保持同级结构：

1. `研究项目库`
2. `研究发起`
3. `指导审批`
4. `共同验收`

同时保留一个 `研究/实验首页` 作为统计看板和流程入口。

### 模块首页建议展示

1. 进行中研究批次数
2. 待指导审批数
3. 待共同验收数
4. 已完成阶段数
5. 最近研究批次
6. 快速入口卡片

建议视觉风格保持与当前 AI CATS 一致，但使用更偏“研究”气质的配色，例如金黄、深蓝、青绿的轻玻璃组合，避免和“配件生产”完全同色。

## 角色设计

### 1. V1 实施建议

第一版不新增底层角色编码，直接复用现有 QC 权限模型：

| 当前角色编码 | 研究模块中的显示名称 |
| --- | --- |
| `qc_controller` | 研发人员 |
| `qc_inspector` | 指导/验收人员 |
| `general_manager` / `gm_assistant` / `superadmin` | 管理角色，保持不变 |

也就是说：

1. 权限上继续沿用当前 `QCService` 的判断结构
2. UI 文案层做别名替换
3. 后续如果研究模块要独立授权，再拆真正的 `researcher` / `research_reviewer` 角色编码

### 2. 角色职责

#### 研发人员

1. 创建研究项目模板
2. 发起研究批次
3. 上传立项资料、实验方案、补充材料
4. 查看指导建议并补充材料
5. 在共同验收阶段签字确认

#### 指导/验收人员

1. 查看分配给自己的研究批次
2. 对研究资料进行审批
3. 给出指导建议、退回意见、补充要求
4. 在共同验收阶段签字确认

#### 管理角色

1. 查看全局研究进度
2. 介入审批、回退、问题排查
3. 查看所有历史记录

## 业务对象设计

### 1. 研究项目模板

作用类似“工件库”，但不是物料库，而是研究课题或实验模板的基础档案。

建议字段：

| 字段 | 说明 |
| --- | --- |
| `project_code` | 项目编号，唯一 |
| `project_name` | 项目名称 |
| `project_category` | 项目分类，可预留：方法开发 / 应用验证 / 失效分析 / 定制研究 |
| `research_direction` | 研究方向或主题 |
| `creator_id` | 创建人 |
| `created_at` / `updated_at` | 时间戳 |

### 2. 研究批次

作用类似“工件订单”，是一条真正执行中的研究任务实例。

建议字段：

| 字段 | 说明 |
| --- | --- |
| `batch_no` | 研究批次号，唯一 |
| `project_id` | 关联研究项目模板 |
| `project_name_snapshot` | 项目名称快照 |
| `sample_quantity` | 样品数量 / 实验数量 |
| `researcher_id` | 研发人员 |
| `reviewer_id` | 指导/验收人员 |
| `status` | 当前状态 |
| `initiated_at` | 发起完成时间 |
| `review_completed_at` | 指导审批完成时间 |
| `accepted_at` | 双方共同验收完成时间 |
| `returned_at` | 退回时间 |
| `return_reason` | 退回原因 |
| `created_at` / `updated_at` | 时间戳 |

### 3. 研究附件

研究模块必须支持与生产模块相同级别的附件追溯，但附件语义要改成研究场景。

建议附件类型如下：

| 附件类型编码 | UI 名称 | 用途 |
| --- | --- | --- |
| `initiation_material` | 立项资料 | 需求背景、客户资料、前置报告、样品照片、问题描述 |
| `research_material` | 研究资料 | 谱图、参考数据、实验原始输入、外部参考文件 |
| `experiment_plan` | 实验方案 | SOP、步骤设计、参数方案、变量控制方案 |
| `validation_item` | 观察项 / 验证目标 | 需要指导方重点审核的条目 |
| `risk_note` | 风险提示 / 补充说明 | 研究限制、注意事项、开放问题 |

### 4. 批次阶段文件

对应当前配件生产里的分区上传文件，建议改成：

| 当前生产语义 | 研究模块语义 |
| --- | --- |
| 图纸批注文件 | 立项补充资料 |
| 生产凭证 | 过程记录 / 阶段结果 |
| 备注批注文件 | 补充说明附件 |

### 5. 批次历史记录

研究批次必须保留不可篡改的历史记录卡片，记录：

1. 操作时间
2. 操作人
3. 行为名称
4. 行为说明

建议至少覆盖：

1. 创建研究批次
2. 保存草稿
3. 提交指导审批
4. 保存指导审批草稿
5. 审批通过
6. 审批退回
7. 研发人员确认
8. 指导/验收人员确认
9. 取消确认
10. 验收回退

## 3. 指导审批

这是研究模块里最接近“质量检测”的部分，但交互语义不能是“检测结果”，而应是“审批结论 + 指导建议”。

### 列表页

建议命名：

`指导审批`

展示字段：

1. 批次号
2. 项目名称
3. 研发人员
4. 指导/验收人员
5. 状态
6. 待处理时长

### 详情页

审批项建议基于附件逐项展开，但术语改为研究语义：

1. 立项资料审核
2. 研究资料审核
3. 实验方案审核
4. 观察项 / 验证目标审核
5. 风险提示查看
6. 过程记录 / 阶段结果查看

每个审核项建议包含：

1. 审批结论
   - `通过`
   - `需补充`
2. 指导建议
3. 可选反馈附件

### 审批结果逻辑

1. 如果全部通过，则进入“待共同验收”
2. 如果任一关键项为“需补充”，则批次退回研发人员
3. 退回后研发人员可补充材料并再次提交

### 为什么不继续叫“质量检测”

因为研究场景更强调：

1. 指导
2. 审批
3. 反馈
4. 迭代

而不是简单的合格 / 不合格判断。

## 4. 共同验收

这是研究模块里最接近“验收”的部分，但业务意义是“该阶段研发完成并归档”。

### 列表页

建议展示：

1. 批次号
2. 项目名称
3. 研发人员签署状态
4. 指导/验收人员签署状态
5. 当前状态

### 详情页

展示内容：

1. 研究项目信息
2. 本批次全部材料
3. 指导审批记录
4. 历史记录
5. 双方签字卡片

### 签字规则

1. 研发人员可签自己的确认
2. 指导/验收人员可签自己的确认
3. 两边都签完后，状态切换为 `阶段研发完成`
4. 支持 `取消确认`
5. 支持管理角色回退

### 完成后的语义

建议不要叫“入库”，而叫：

1. `阶段归档`
2. `研发阶段完成`

如果后续确实需要把研究结果转入“装配/出厂”或“配件生产”，再增加跨模块引用逻辑，不在这一版里强行耦合。

## 状态机设计

建议研究模块使用独立状态枚举，但节奏对齐配件生产：

| 状态编码 | 显示文案 | 说明 |
| --- | --- | --- |
| `draft` | 草稿 | 尚未正式提交 |
| `research_pending` | 研究准备中 | 发起页编辑中 |
| `research_submitted` | 待指导审批 | 已由研发人员提交 |
| `review_completed` | 指导完成 | 审批通过，待双方验收 |
| `accepted` | 阶段研发完成 | 双方共同验收完成 |
| `returned` | 已退回补充 | 指导方退回给研发人员 |

### 状态流转

```text
草稿
  -> 研究准备中
  -> 待指导审批
  -> 指导完成
  -> 阶段研发完成

待指导审批
  -> 已退回补充
  -> 研究准备中
  -> 待指导审批
```

### 与配件生产的关系

实现层可以复用当前状态展示组件、时间戳机制和历史记录机制。  
但研究模块应使用自己的状态文案，不直接展示 `qc_pending`、`inspection_completed` 之类的生产术语。

## 与配件生产的边界

研究/实验模块第一版明确不包含以下能力：

1. 库存增减
2. 物料入库
3. ERP 合同联动
4. 自动图表分析
5. 仪器原始数据解析
6. 多指导人并行审批
7. 跨模块自动转单

### 为什么不做这些

因为本轮目标是先把“研究发起 -> 指导审批 -> 双方验收 -> 阶段归档”的闭环搭起来。  
如果一开始就把生产、ERP、装配模块、图表分析一起揉进去，耦合会很重，后续维护成本会迅速上升。

## 推荐实施结论

这套“研究/实验”模块，最合适的做法不是把“配件生产”生硬换名，而是：

1. 复用“配件生产”的结构和交互节奏
2. 重建研究语义的数据对象和文案
3. 保持独立表结构，避免未来与生产流程互相污染
4. 先做闭环，再逐步增加数据分析能力

如果按这个方案实施，研究模块会在用户体验上足够熟悉，但在业务边界上又足够清晰，后续无论扩展“实验数据分析”还是“成果转装配/出厂”，都更稳。
